# Кейсы

Файл кейса — это ограничения, под которыми считается задача. ТЗ §11: на
проверку выдаётся **набор ограничений плюс история разработки**, модель та же.
Поэтому ограничения живут в файле, а не в коде, и подмена кейса не требует
правок и пересборки.

Загрузчик строгий: неизвестный раздел — ошибка, а не игнор. Комментарии внутри
JSON поэтому невозможны, и обоснование значений лежит здесь.

## `baseline-feasible.json`

Кейс, в котором эталонное расписание организаторов физически выполнимо.

Дефолтный `config/competition-constraints.json` задаёт
`external_water_m3_per_day = 0` при `water_reinjection_fraction = 1.0`, то есть
«закачивай не больше добытой воды». **Эталон организаторов этому не
удовлетворяет.** Замер на базовом отклике:

| | |
|---|---:|
| закачано за 224 шага | 11.662 млн м³ |
| добыто воды | 5.019 млн м³ |
| **дефицит** | **6.642 млн м³** |
| доля закачки из внешнего источника | 57% |
| средний дефицит | 974 м³/сут |
| **пиковый шаговый дефицит** | **1364 м³/сут** |

Следствие видно прямо в прогонах: у самого якоря 224 нарушения
`WATER_SUPPLY_LIMIT_EXCEEDED` — по одному на каждый шаг, и они одинаковы у
всех одиннадцати кандидатов пакета (`tools/surrogate_anchor_doe.py`).
Ограничение относится к конфигурации, а не к расписанию.

Дальше это ломает весь тракт сдачи: поиск вынужден работать в режиме
водяного голода, которого не было в обучении суррогата. Там суррогат вне
области применимости (сценарный OOD 86.9…146.0 при пороге 11.42), его ЧДД
уходит в минус, неподвижная точка не сходится, и `aios_cli.e2e` завершается
отказом.

`external_water_m3_per_day = 1364.0` **выведено из эталона, а не назначено**:
это пиковый шаговый дефицит базового прогона, то есть верхняя граница того,
что расписанию организаторов реально требуется.

Куратор на чекпоинте 31.08 (00:20:57): «на тестовом кейсе будет предоставлено
некоторый объём жидкости в размере n, который вы можете закачивать
дополнительно». Когда тестовый кейс опубликуют, это поле заменяется их `n` —
файл кейса для того и существует.
