# Конфигурация: файл кейса

Кейс — это один JSON-файл в формате контракта `Constraints`
(`backend/core/contracts/constraints.py`). Он полностью описывает условия задачи:
годовые лимиты, простои скважин и параметры инфраструктуры. Больше нигде условия
задачи не задаются — чтобы воспроизвести прогон, достаточно этого файла, дека
Model_Z и коммита.

Запуск на кейсе:

```
PYTHONPATH=. python -m backend.presentation.cli.run full --case config/cases/base.json
```

Без `--case` читается `config/competition-constraints.json` (или путь из
переменной окружения `AIOS_CONSTRAINTS_PATH`). `config/cases/base.json`
совпадает с этим файлом по содержанию: это базовый кейс соревнования.

Тот же формат экспортирует и импортирует редактор ограничений в интерфейсе
(«Решения → Ограничения»), поэтому кейс организаторов можно открыть в интерфейсе,
а отредактированный сценарий — сохранить и подать в CLI.

## Правила проверки

- Неизвестный раздел верхнего уровня — **ошибка** с именем раздела, а не
  молчаливый пропуск. Молча потерянное ограничение хуже отказа.
- Неизвестный ключ в `infrastructure` — **ошибка** с именем ключа. Опечатка
  `compensaton_min` не должна тихо отключить коридор компенсации.
- Разделы `new_wells`, `oil_limits`, `commissioning_shifts` распознаются и
  **отклоняются с объяснением причины**: они осмысленны, но пока не поддержаны
  трактом. Отказ честнее, чем принять файл и проигнорировать ограничение.
- Все разделы необязательны. Пустой документ `{}` — это «нет ограничений сверх
  физических», а не «данных нет».

## Разделы верхнего уровня

| Раздел | Тип | Единица | Смысл |
| --- | --- | --- | --- |
| `injection_limits` | объект `год → число` | м³/сут | Потолок суммарной закачки по полю в этом календарном году |
| `liquid_limits` | объект `год → число` | м³/сут | Потолок суммарного отбора жидкости по полю |
| `production_floors` | объект `год → число` | т/сут | Пол по добыче нефти: цель, ниже которой опускаться нельзя |
| `watercut_limits` | объект `год → число` | доля 0…1 | Потолок обводнённости. Проценты отклоняются: `50.0` — ошибка, `0.5` — верно |
| `well_outages` | массив объектов | — | Плановые остановки скважин, см. ниже |
| `infrastructure` | объект | — | Параметры инфраструктуры и физики, см. ниже |

Год задаётся строкой или числом (`"2007"` и `2007` равнозначны — JSON-ключи
всегда строки). Отрицательные лимиты и `NaN` отклоняются. Один и тот же год
дважды в одном разделе — ошибка.

**Значение по умолчанию для всех четырёх годовых разделов — пустой объект.**
Организаторы в базовой постановке годовых лимитов не задали: единственное
ограничение базового кейса — физика дека и коридор компенсации. Как только в
тестовом кейсе появятся числа, они попадают сюда без изменений в коде.

### `well_outages`

Массив объектов. Скважина считается недоступной на шагах управления
`control_step_from … control_step_to` включительно.

| Поле | Тип | Смысл |
| --- | --- | --- |
| `well` | строка, непустая | Идентификатор скважины как в деке Model_Z |
| `control_step_from` | целое 0…223 | Первый шаг управления простоя, включительно |
| `control_step_to` | целое 0…223 | Последний шаг простоя, включительно |

Горизонт — 224 шага управления (`N_INTERVALS`, `backend/core/contracts/schedule.py`):
это сетка контрольных дат Model_Z от 01.01.2007. Шаг вне горизонта и
`control_step_from > control_step_to` — ошибки с указанием индекса элемента.

По умолчанию — пустой массив: в базовом кейсе организаторы простоев не объявляли.

### `infrastructure`

Свободных ключей здесь нет: допустимы ровно семь перечисленных.

| Ключ | Тип | Единица | Смысл | Значение по умолчанию и откуда взято |
| --- | --- | --- | --- | --- |
| `water_reinjection_fraction` | число 0…1 | доля | Какая часть добытой воды возвращается в закачку. Задаёт баланс воды: `Σ закачка(k) ≤ Σ добытая вода(k − лаг) · доля + n`. Если ключ не задан — проверка баланса воды не выполняется вовсе, источник воды считается неограниченным | `1.0` — вся добытая вода доступна к закачке. Это допущение нашей стороны при отсутствии данных организаторов, а не измерение. Тестовый кейс должен переопределить значение или убрать ключ |
| `water_reinjection_lag_steps` | целое ≥ 0 | шаги управления | Задержка между добычей воды и её доступностью для закачки (подготовка, транспорт) | `0` — мгновенная доступность. Данных о лаге подготовки в постановке нет; ноль — самый мягкий вариант, он не создаёт ложных нарушений |
| `external_water_m3_per_day` | число ≥ 0 | м³/сут | **Объём `n` организаторов**: вода из внешнего источника, которую можно закачивать сверх добытой. Куратор, чекпоинт 31.08 (00:20:57): «на тестовом кейсе будет предоставлено некоторый объём жидкости в размере n… который вы можете закачивать дополнительно» | `0.0` — внешнего источника нет. Значение `n` придёт в тестовом кейсе; до этого добавлять его нельзя, иначе оптимизатор получит воду, которой у него нет |
| `compensation_min` | число ≥ 0 | доля (1.0 = 100 %) | Нижняя граница коридора компенсации отбора закачкой в **пластовых** условиях: `C(k) = V_закачки / V_отбора` | `0.85`. Измерено по базовому прогону организаторов как `min_k C_base(k) − δ` при `δ = 0.05` |
| `compensation_max` | число ≥ `compensation_min` | доля | Верхняя граница того же коридора. Он закрывает ловушку «разогнать закачку до максимума»: заказчик определил её именно через компенсацию (лекция 12.08, 01:02) | `1.15`. Измерено как `max_k C_base(k) + δ` при `δ = 0.05` |
| `compensation_enforcement` | `"diagnostic"` \| `"hard"` | — | `diagnostic` — выход за коридор попадает в отчёт, но расписание принимается; `hard` — выход за коридор блокирует расписание | `"diagnostic"`. Для сдачи переключается в `"hard"`: пока коридор не подтверждён на тестовом кейсе, блокировать по нему рискованно |
| `compensation_scope` | `"field"` \| `"groups"` \| `"field_and_groups"` | — | Где проверяется коридор: только по полю, только по участкам или и там, и там | `"field_and_groups"`. Компенсация, сошедшаяся по полю, может быть нарушена на участке; проверяем обе области |

Границы коридора задаются **только парой**: `compensation_min` без
`compensation_max` (и наоборот) — ошибка. Если не задана ни одна, коридор
выключен.

## Пример: кейс с возмущениями

```json
{
  "injection_limits": { "2010": 42000.0 },
  "liquid_limits": { "2010": 38000.0, "2011": 36000.0 },
  "production_floors": { "2010": 1500.0 },
  "watercut_limits": { "2012": 0.95 },
  "well_outages": [
    { "well": "P12", "control_step_from": 48, "control_step_to": 51 }
  ],
  "infrastructure": {
    "external_water_m3_per_day": 5000.0,
    "compensation_min": 0.9,
    "compensation_max": 1.1,
    "compensation_enforcement": "hard",
    "compensation_scope": "field_and_groups"
  }
}
```

Здесь `water_reinjection_fraction` не задан, поэтому проверка баланса воды
отключена, а объём закачки ограничен только коридором компенсации и
`injection_limits`.

## Прочие файлы каталога

| Файл | Назначение |
| --- | --- |
| `competition-constraints.json` | Кейс по умолчанию, читается когда `--case` не передан. Совпадает с `cases/base.json` |
| `cases/base.json` | Базовый кейс соревнования в каталоге кейсов |
| `opm-champion.json` | Ссылка на подтверждённый OPM прогон-incumbent. Не кейс |
| `opm-active-npv-calibration.json` | Калибровка экономической головы по прогонам OPM. Не кейс |
