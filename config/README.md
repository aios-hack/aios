# Конфигурация: файл кейса

Кейс — это один JSON-файл в формате контракта `Constraints`
(`backend/core/contracts/constraints.py`). Он полностью описывает условия задачи:
годовые лимиты, простои скважин и параметры инфраструктуры. Больше нигде условия
задачи не задаются — чтобы воспроизвести прогон, достаточно этого файла, дека
Model_Z и коммита.

Запуск на кейсе:

```
PYTHONPATH=. python -m backend.presentation.cli.run full --case config/cases/base.json
```

Без `--case` читается `config/competition-constraints.json` (или путь из
переменной окружения `AIOS_CONSTRAINTS_PATH`). `config/cases/base.json`
совпадает с этим файлом по содержанию: это базовый кейс соревнования.

Тот же формат экспортирует и импортирует редактор ограничений в интерфейсе
(«Решения → Ограничения»), поэтому кейс организаторов можно открыть в интерфейсе,
а отредактированный сценарий — сохранить и подать в CLI.

## Правила проверки

- Неизвестный раздел верхнего уровня — **ошибка** с именем раздела, а не
  молчаливый пропуск. Молча потерянное ограничение хуже отказа.
- Неизвестный ключ в `infrastructure` — **ошибка** с именем ключа. Опечатка
  `compensaton_min` не должна тихо отключить коридор компенсации.
- Блокирующее ограничение инфраструктуры без парного `<параметр>_source` —
  **ошибка** с именем недостающего поля. Число, способное отклонить расписание,
  обязано назвать своего автора: организаторов или нас.
- Разделы `new_wells`, `commissioning_shifts` распознаются и
  **отклоняются с объяснением причины**: они осмысленны, но пока не поддержаны
  трактом. Отказ честнее, чем принять файл и проигнорировать ограничение.
- Все разделы необязательны. Пустой документ `{}` — это «нет ограничений сверх
  физических», а не «данных нет».

## Разделы верхнего уровня

| Раздел | Тип | Единица | Смысл |
| --- | --- | --- | --- |
| `injection_limits` | объект `год → число` | м³/сут | Потолок суммарной закачки по полю в этом календарном году |
| `liquid_limits` | объект `год → число` | м³/сут | Потолок суммарного отбора жидкости по полю |
| `production_floors` | объект `год → число` | т/сут | Пол по добыче нефти: цель, ниже которой опускаться нельзя |
| `oil_limits` | объект `год → число` | т/сут | Потолок суммарной добычи нефти по полю: квота, выше которой подниматься нельзя |
| `watercut_limits` | объект `год → число` | доля 0…1 | Потолок обводнённости. Проценты отклоняются: `50.0` — ошибка, `0.5` — верно |
| `well_outages` | массив объектов | — | Плановые остановки скважин, см. ниже |
| `infrastructure` | объект | — | Параметры инфраструктуры и физики, см. ниже |

Год задаётся строкой или числом (`"2007"` и `2007` равнозначны — JSON-ключи
всегда строки). Отрицательные лимиты и `NaN` отклоняются. Один и тот же год
дважды в одном разделе — ошибка.

**Значение по умолчанию для всех пяти годовых разделов — пустой объект.**
Организаторы в базовой постановке годовых лимитов не задали: единственное
ограничение базового кейса — физика дека и коридор компенсации. Как только в
тестовом кейсе появятся числа, они попадают сюда без изменений в коде.

### `oil_limits` — потолок по нефти

`oil_limits` — это квота на добычу нефти: тот самый потолок, который в перечне
возмущений ТЗ назван «квотой ОПЕК». Единица — **тонны в сутки**, та же, что у
`production_floors`, и это не случайность: две границы описывают один и тот же
поток нефти с двух сторон, и мерить их разными величинами значило бы завести
две несравнимые шкалы для одного ограничения.

**Семантика — пошаговая суточная ставка, а не годовая сумма.** Проверяемое
неравенство одно и то же на каждом шаге управления `k` того года, на который
задана квота:

```
Σ добыча нефти(k) ≤ oil_limits[год]
```

Сумма берётся по всему фонду за шаг, из тех же `StateAtDate`, из которых
считаются `liquid_limits`, `injection_limits` и `production_floors`. Нарушением
считается превышение на **любом** шаге, и нарушение несёт номер именно этого
шага — так же, как у уже существующих лимитов. Годовой суммарный объём здесь не
считается вовсе: годовая сумма — другое ограничение с другой физикой, и
подменять им пошаговый потолок значило бы принять кейс и посчитать не то, что в
нём написано.

Нарушение — `OIL_LIMIT_EXCEEDED`, **блокирующее**: расписание, вышедшее за
квоту, отклоняется. Отчёт о применённых ограничениях получает запись
`oil_limits` со статусом `checked` (с числом нарушений) или `not_set`, если
раздел в кейсе пуст.

Источника (`<параметр>_source`) у раздела нет: как и остальные годовые разделы,
он приходит из кейса целиком и по построению принадлежит организаторам.

`oil_limits` и `production_floors` заданные на один год образуют коридор
`production_floors[год] … oil_limits[год]`. Пустой коридор (потолок ниже пола)
разделами не проверяется: это противоречие внутри самого кейса, и обе границы
дадут нарушение на каждом шаге — молчаливое «исправление» одной из них было бы
подстановкой числа за организаторов.

### `well_outages`

Массив объектов. Скважина считается недоступной на шагах управления
`control_step_from … control_step_to` включительно.

| Поле | Тип | Смысл |
| --- | --- | --- |
| `well` | строка, непустая | Идентификатор скважины как в деке Model_Z |
| `control_step_from` | целое 0…223 | Первый шаг управления простоя, включительно |
| `control_step_to` | целое 0…223 | Последний шаг простоя, включительно |

Горизонт — 224 шага управления (`N_INTERVALS`, `backend/core/contracts/schedule.py`):
это сетка контрольных дат Model_Z от 01.01.2007. Шаг вне горизонта и
`control_step_from > control_step_to` — ошибки с указанием индекса элемента.

По умолчанию — пустой массив: в базовом кейсе организаторы простоев не объявляли.

### `infrastructure`

Свободных ключей здесь нет: допустимы ровно тринадцать перечисленных ниже
параметров и парные к ним ключи `<параметр>_source` (см. «Источник
ограничения»).

| Ключ | Тип | Единица | Смысл | Значение по умолчанию и откуда взято |
| --- | --- | --- | --- | --- |
| `water_supply_unlimited` | `true` \| `false` | — | Явное объявление «источник воды не ограничен»: баланс воды не проверяется вовсе. Несовместим с остальными тремя водяными ключами | `false` — источник воды ограничен, как только задан хотя бы один водяной ключ |
| `water_reinjection_fraction` | число 0…1 | доля | Какая часть добытой воды возвращается в закачку. Задаёт баланс воды: `Σ закачка(k) ≤ Σ добытая вода(k − лаг) · доля + n` | `1.0` — вся добытая вода доступна к закачке, если задан любой другой водяной ключ. Это допущение нашей стороны при отсутствии данных организаторов, а не измерение; факт подстановки помечается в отчёте кейса |
| `water_reinjection_lag_steps` | целое ≥ 0 | шаги управления | Задержка между добычей воды и её доступностью для закачки (подготовка, транспорт) | `0` — мгновенная доступность. Данных о лаге подготовки в постановке нет; ноль — самый мягкий вариант, он не создаёт ложных нарушений |
| `external_water_m3_per_day` | число ≥ 0 | м³/сут | **Объём `n` организаторов**: вода из внешнего источника, которую можно закачивать сверх добытой. Куратор, чекпоинт 31.08 (00:20:57): «на тестовом кейсе будет предоставлено некоторый объём жидкости в размере n… который вы можете закачивать дополнительно». Подробнее — раздел «Внешняя вода `n`» ниже | `0.0` — внешнего источника нет. Значение `n` придёт в тестовом кейсе; до этого добавлять его нельзя, иначе оптимизатор получит воду, которой у него нет |
| `water_safety_factor` | число в (0, 1] | доля | Запас на потолке закачки: команда закачки умножается на этот множитель. Это **наше допущение**, а не требование организаторов, поэтому по умолчанию оно ничего не режет. Значение `0.85` раньше было зашито в `water_baseline_run.py`; теперь его задают явно в кейсе, и в отчёте прогона видно, откуда оно взялось (`water_safety_factor_source`) | `1.0` — источник `assumption`: запас не применяется. Наш собственный резерв не должен быть неотличим от ограничения кейса |
| `compensation_min` | число ≥ 0 | доля (1.0 = 100 %) | Нижняя граница коридора компенсации отбора закачкой в **пластовых** условиях: `C(k) = V_закачки / V_отбора` | `0.85`. Измерено по базовому прогону организаторов как `min_k C_base(k) − δ` при `δ = 0.05` |
| `compensation_max` | число ≥ `compensation_min` | доля | Верхняя граница того же коридора. Он закрывает ловушку «разогнать закачку до максимума»: заказчик определил её именно через компенсацию (лекция 12.08, 01:02) | `1.15`. Измерено как `max_k C_base(k) + δ` при `δ = 0.05` |
| `compensation_enforcement` | `"diagnostic"` \| `"hard"` | — | `diagnostic` — выход за коридор попадает в отчёт, но расписание принимается; `hard` — выход за коридор блокирует расписание | `"diagnostic"`. Для сдачи переключается в `"hard"`: пока коридор не подтверждён на тестовом кейсе, блокировать по нему рискованно |
| `compensation_scope` | `"field"` \| `"groups"` \| `"field_and_groups"` | — | Где проверяется коридор: только по полю, только по участкам или и там, и там. Значения с участками требуют передать в валидатор нарезку `Groups`, иначе проверка завершается ошибкой. Подробности — раздел «Область проверки компенсации» ниже | `"field_and_groups"`. Компенсация, сошедшаяся по полю, может быть нарушена на участке; проверяем обе области |
| `bhp_producer_min_bar` | число > 0 | бар | Нижний предел забойного давления добывающей: `WBHP` ниже него — блокирующее нарушение `BHP_BELOW_PRODUCER_LIMIT` | `50.0` — предел дека Model_Z. Раньше был зашит константой в `backend/domain/schedule/validate_dynamic.py`; теперь константа лишь хранит это же умолчание, а истина берётся из кейса |
| `bhp_injector_max_bar` | число > `bhp_producer_min_bar` | бар | Верхний предел забойного давления нагнетательной: `WBHP` выше него — блокирующее нарушение `BHP_ABOVE_INJECTOR_LIMIT` | `300.0` — предел дека Model_Z, та же история, что и у нижнего предела |
| `pressure_floor_bar` | число > 0 | бар | Пол среднего пластового давления поля: `FPR` ниже него — блокирующее нарушение `FIELD_PRESSURE_BELOW_FLOOR` | **умолчания нет.** Если ключ не задан, проверка не запускается и в отчёте стоит `not_set` |
| `pressure_ceiling_bar` | число > `pressure_floor_bar` | бар | Потолок среднего пластового давления поля: `FPR` выше него — блокирующее нарушение `FIELD_PRESSURE_ABOVE_CEILING` | **умолчания нет**, та же история, что и у пола |

Границы коридора задаются **только парой**: `compensation_min` без
`compensation_max` (и наоборот) — ошибка. Если не задана ни одна, коридор
выключен.

### Область проверки компенсации: `compensation_scope`

Коридор `C(k) = V_закачки / V_отбора` можно требовать на двух разных уровнях
агрегации, и это принципиально разные ограничения. Ключ `compensation_scope`
выбирает, какие из них проверяются.

| Значение | Что проверяется | Запись в отчёте `infrastructure.compensation` | Запись в отчёте `infrastructure.compensation_scope` |
| --- | --- | --- | --- |
| `"field"` | Только по полю целиком: отбор и закачка суммируются по всему фонду за шаг управления | `checked` с числом нарушений по полю | `checked`, `n_violations = 0` — групповой разрез кейсом не запрошен |
| `"groups"` | Только по участкам: свои суммы отбора и закачки внутри каждого участка на каждом шаге | `not_set` — разрез по полю целиком не запрашивался | `checked` с числом нарушений по участкам |
| `"field_and_groups"` | Обе области сразу | `checked` с числом нарушений по полю | `checked` с числом нарушений по участкам |

Нарушения обеих областей несут те же два вида, что и раньше —
`COMPENSATION_OUT_OF_CORRIDOR` и `COMPENSATION_UNDEFINED`. Различает их текст:
поле целиком помечается словами «поле целиком», участок — «участок `<id>`».
Блокирующими они становятся ровно тогда же, когда и раньше: при
`compensation_enforcement = "hard"`. При `"diagnostic"` нарушение попадает в
отчёт, но расписание принимается.

**Зачем разрез по участкам.** Компенсация, сошедшаяся по полю, может быть
грубо нарушена внутри участка: недобор закачки в одном месте гасится её
избытком в другом, и среднее по полю выглядит здоровым. Проверка по участкам
ловит именно этот перекос — нарушение на одном участке видно даже тогда, когда
по полю `C(k)` строго в коридоре.

**Что требуется для проверки по участкам.** Валидатору нужна нарезка фонда —
`Groups` из `backend/core/contracts/connectivity.py`, которую строит
`backend/domain/connectivity/groups.py` по измеренной матрице влияния. Она
передаётся в `validate_dynamic` необязательным аргументом `groups`.

**Что происходит при отсутствии групп.** Если кейс объявил `"groups"` или
`"field_and_groups"`, а `Groups` в валидатор не переданы, проверка завершается
ошибкой `ValueError` и расписание не получает никакого статуса. Это осознанное
решение, а не строгость ради строгости: молчаливый пропуск дал бы `sound=true`
по ограничению, которое никто не считал, — ровно та дыра, ради закрытия
которой разрез и вводился. Область `"field"` групп не требует и работает без
них.

Нарезка обязана покрывать весь фонд: если в отклике встретилась скважина, не
попавшая ни в один участок, это тоже ошибка — считать `C(k)` по неполной
нарезке значит объявить проверку выполненной там, где часть отбора и закачки
не учтена. Скважина может принадлежать нескольким участкам сразу; тогда её
объёмы входят в сумму каждого из них.

Нулевой отбор внутри участка обрабатывается так же, как нулевой отбор по полю:
это `COMPENSATION_UNDEFINED`, а не `C(k) = 0` и не молчаливый пропуск. Делить
на ноль нельзя, поэтому вместо выдуманного отношения в отчёт идёт явная
запись: отбор равен нулю, закачано столько-то, в коридор не проверялось.

### Пластовое давление: `pressure_floor_bar` и `pressure_ceiling_bar`

Пластовое давление куратор назвала прямым ограничением, и оно проверяется
валидатором по полевому вектору `FPR` (среднее давление поля) на каждом шаге
управления. Каждый из двух пределов задаётся независимо: можно объявить только
пол, только потолок или оба. Если задана пара, пустой коридор (потолок не выше
пола) — ошибка.

**Умолчаний у этих двух ключей нет, и это осознанное решение.** Известно, что
начальное равновесное давление дека Model_Z — 119…125 бар (строки `EQUIL` в
`Model_Z_init.inc`). Соблазн подставить пол «где-то оттуда» ровно тот же, что
однажды уже дал коридор компенсации `0.85…1.15`, назначенный нами и внешне
неотличимый от условия организаторов. Поэтому: **предел, которого нет в кейсе,
не назначается за организаторов**. Проверка тогда не запускается, а в отчёте о
применённых ограничениях `infrastructure.field_pressure` получает статус
`not_set` с указанием обоих недостающих ключей — молчания нет, есть явная
запись «не проверялось, потому что не задано».

Обратная сторона того же принципа: **если предел задан, а серии `FPR` нет,
валидатор падает с ошибкой, а не пропускает проверку.** Давление известно
только после прогона OPM, поэтому «политика включена, серии не передали» — это
не «нарушений не нашли», а «посчитать не смогли». Компонент, который не может
посчитать результат, обязан сообщить об ошибке; иначе повторяется дефект, при
котором ограничение объявлено, проверка молчит, а `sound=true` врёт.

Оба предела блокирующие, поэтому парный `<параметр>_source` для них
обязателен — кейс с `pressure_floor_bar` без `pressure_floor_bar_source`
отклоняется с именем недостающего поля.

#### Проекция оси: давление читается как уровень

`FPR` приходит по 371 дате дека, а нарушения нумеруются по 224 шагам
управления, и соглашение о переносе здесь отличается от объёмного:

| Величина | Что индексируется | Проекция |
| --- | --- | --- |
| `IntervalResponse` (объёмы) | **разности** `cumulative[i+1] − cumulative[i]` | `interval[k] = raw_diff[146 + k]` |
| `StateAtDate`, `FPR` (давление) | **уровни** | `level[k] = raw[147 + k]` |

Давление — уровень, а не приращение, поэтому оно следует проекции
`StateAtDate`: `control_step = deck_date_index − 147`. Физически это состояние
пласта **после** того, как управление шага `k` вступило в силу — именно то, что
и проверяется: нарушил ли наш план предел давления. Взять здесь `146 + k`
значило бы сдвинуть весь вердикт на месяц и приписать шагу давление, сложившееся
до его команд.

### Материальный баланс

Помимо ограничений кейса валидатор сверяет материальный баланс пласта по тем же
полевым сериям: изменение запаса обязано равняться потоку. По нефти —
`ΔFOIP = −ΔFOPT`, по воде — `ΔFWIP = ΔFWIT − ΔFWPT`, допуск относительной
невязки `0.01`. Расхождение выше допуска даёт нарушение `MATERIAL_BALANCE_BROKEN`.

Баланс берётся агрегатом по всему горизонту, а не шаг к шагу: `FWIP` Model_Z —
около 2.58·10¹¹ м³, а `UNSMRY` хранит `REAL` в четырёх байтах, поэтому шум
округления одного шага (≈30 000 м³) больше самого месячного притока
(1 500–2 500 м³). Межшаговая невязка была бы артефактом `float32`, а не браком
физики.

Это не параметр кейса, а физическая проверка, поэтому источника у неё нет и в
таблице источников она не появляется. В отчёте о применённых ограничениях у неё
своя запись `material_balance`: если полевые серии не переданы, статус
`not_set`, если переданы — `checked` с числом нарушений.

Пределы забойного давления задают коридор `bhp_producer_min_bar …
bhp_injector_max_bar`. Пустой коридор (верхний предел не выше нижнего) —
ошибка. Каждый из двух пределов можно задать отдельно, второй тогда берётся из
умолчания дека. Изменение предела в кейсе меняет вердикт валидатора: расписание,
принятое при `bhp_producer_min_bar = 50`, при `90` может быть отклонено.

## Источник ограничения: `<параметр>_source`

Главный риск постановки — не ошибка в числе, а невозможность отличить **условие
организаторов** от **нашего инженерного допущения**. Коридор компенсации
`0.85…1.15` назначили мы (базовый прогон организаторов идёт `1.20…1.46`), запас
по воде `0.85` тоже был наш, доля реинжекции подставляется по умолчанию. Снаружи
все эти числа выглядели одинаково — как «данные задачи».

Поэтому у каждого параметра инфраструктуры есть парный ключ `<параметр>_source`
с одним из трёх значений:

| Значение | Что означает | Кто отвечает за число |
| --- | --- | --- |
| `organizer` | Условие организаторов: пришло из постановки, дека Model_Z, лекции или ответа куратора | Организаторы |
| `diagnostic` | Диагностический ориентир: измерен нами по базовому прогону, служит сигналом в отчёте, а не запретом | Мы, но как наблюдение |
| `assumption` | Допущение нашей стороны при отсутствии данных | Мы целиком |

Правила проверки:

- **Для блокирующего ограничения источник обязателен.** Кейс, где задан
  блокирующий параметр без парного `_source`, **отклоняется** с именем
  недостающего поля: `infrastructure.bhp_producer_min_bar_source: ограничение
  infrastructure.bhp_producer_min_bar блокирует расписание, поэтому его
  источник обязателен`. Молча принять число, которое остановит расписание, и не
  знать, чьё оно, — ровно тот отказ доверия, ради которого поле и вводится.
- **Для диагностического — по желанию.** Коридор компенсации в режиме
  `diagnostic` попадает в отчёт, но расписание не блокирует, поэтому источник у
  него необязателен. Как только `compensation_enforcement` переключат в `hard`,
  его следует объявить явно.
- `_source` без самого ограничения — ошибка: источник без числа ничего не
  описывает.
- Значение вне тройки `organizer` / `diagnostic` / `assumption` — ошибка с
  именем поля.
- Если параметр в кейсе **не задан вовсе**, источником считается умолчание: у
  пределов забойного давления это `organizer` (числа дека), у остальных
  источника нет и в тексте нарушения будет написано «не объявлен».

### Таблица источников

Столбец «Область» отвечает на вопрос «где именно это ограничение проверяется».
Столбец «Блокирующее» — на вопрос «может ли оно отклонить расписание».

| Ограничение | Единица | Область применения | Блокирующее | Источник в поставляемых кейсах |
| --- | --- | --- | --- | --- |
| `bhp_producer_min_bar` | бар | Каждая добывающая скважина на каждом шаге управления с положительным дебитом жидкости | да | `organizer` — предел дека Model_Z |
| `bhp_injector_max_bar` | бар | Каждая нагнетательная скважина на каждом шаге управления | да | `organizer` — предел дека Model_Z |
| `pressure_floor_bar` | бар | Среднее пластовое давление поля (`FPR`) на каждом шаге управления | да | не задан в поставляемых кейсах: организаторы предела не объявляли, а назначать его от себя нельзя |
| `pressure_ceiling_bar` | бар | Тот же `FPR` на каждом шаге управления | да | не задан в поставляемых кейсах, та же причина |
| `water_reinjection_fraction` | доля 0…1 | Материальный баланс воды по полю на каждом шаге управления | да | `assumption` — данных организаторов о доле возврата нет, взят самый мягкий вариант `1.0` |
| `water_reinjection_lag_steps` | шаги управления | Тот же баланс воды, сдвиг источника | да | `assumption` — данных о лаге подготовки нет, взят `0` |
| `external_water_m3_per_day` | м³/сут | Тот же баланс воды, слагаемое `n` | да | `organizer` — объём `n` из постановки; до тестового кейса он равен `0.0` |
| `water_supply_unlimited` | — | Снимает проверку баланса воды целиком | да | не задан в поставляемых кейсах |
| `compensation_min` | доля | Коридор `C(k)` за шаг управления; где именно — задаёт `compensation_scope` | нет, пока `compensation_enforcement = "diagnostic"` | `diagnostic` — измерено нами по базовому прогону как `min_k C_base(k) − 0.05` |
| `compensation_max` | доля | Тот же коридор | нет, пока режим `diagnostic` | `diagnostic` — измерено нами как `max_k C_base(k) + 0.05` |
| `compensation_enforcement` | — | Переключатель «диагностика / блокировка» для коридора | нет | не задан явно, режим `diagnostic` |
| `compensation_scope` | — | Область проверки коридора: по полю, по участкам или обе | нет, пока режим `diagnostic` | не задан явно, `field_and_groups` |
| `water_safety_factor` | доля (0, 1] | Множитель потолка закачки в поисковике | нет | не задан; при появлении в кейсе — `assumption`, это наш запас |

Годовые разделы (`injection_limits`, `liquid_limits`, `production_floors`,
`oil_limits`, `watercut_limits`) и `well_outages` источника не несут: они
приходят из кейса целиком и по построению принадлежат организаторам. В базовом
кейсе все они пусты.

### Что видно в тексте нарушения

Валидатор больше не говорит просто «предел превышен». В `Violation.detail`
попадают имя поля кейса, источник и путь к файлу кейса:

```text
[BHP_BELOW_PRODUCER_LIMIT] control_step=0, скважина 'P1', значение 10.0:
забойное давление добывающей 10.0 бар ниже предела 90.0 бар;
предел infrastructure.bhp_producer_min_bar, источник organizer
(условие организаторов), кейс config/cases/base.json
```

Если источник у объявленного в кейсе ограничения отсутствует (так бывает у
диагностических), в тексте будет `источник не объявлен (источник не объявлен)`.
Читателю отчёта не нужно открывать код, чтобы понять, чьё это требование.

### Совместимость с уже существующими кейсами

Требование источника сделано **жёстким**, без послаблений для ранее написанных
файлов, а поставляемые кейсы (`config/cases/base.json` и
`config/competition-constraints.json`) дополнены явными источниками. Мягкое
правило «для старых полей источник необязателен» вернуло бы ровно ту проблему,
ради которой поле вводится: кейс без источников проходил бы валидацию, и на
защите мы снова не смогли бы отличить своё число от заданного. Кейс, написанный
до этого изменения и содержащий блокирующий параметр без источника, будет
отклонён с именем недостающего поля — это одна правка в файле, а не поиск по
коду.

### `water_safety_factor` — наш запас, а не условие задачи

Потолок закачки на каждом шаге управления считается в одной функции
`injection_budget_for_step`
(`backend/application/optimization/schedule_search.py`). Она берёт минимум из
источников и называет победителя:

| Источник в трассе | Откуда берётся | Причина ограничения |
| --- | --- | --- |
| `physical_headroom` | максимальная суммарная закачка базового дека × `PHYSICAL_HEADROOM` | физика дека |
| `case_injection_limit` | `injection_limits[год]` | требование кейса |
| `water_balance` | политика воды: `n · доля добытой воды(k − лаг)` | баланс воды кейса |
| `command_margin` | наш запас команды | допущение нашей стороны |
| `water_balance_repair` | ремонт водного баланса после прогноза (`search_run.py`) | реакция на нарушение валидатора |

Первые три — разные ограничения с разными причинами; они не складываются, из
них берётся минимум, и в трассу (`trace_sink["injection_budget"]`) пишется
`binding_source` — какое именно ограничение сработало на этом шаге, — вместе с
вкладом каждого источника. Если ни один источник не задан, потолка нет вовсе, и
закачка не режется.

`command_margin` и `water_safety_factor` — единственные множители нашей
стороны. Оба по умолчанию равны `1.0` в том смысле, что без явного условия кейса
они не отнимают закачку: незадекларированный запас неотличим снаружи от
требования организаторов и занижает результат.

### Внешняя вода `n`

`external_water_m3_per_day` — это тот самый объём `n` из постановки
организаторов: вода, которую разрешено закачивать **дополнительно** к воде,
добытой самим месторождением. Единица — кубические метры в сутки, та же, что у
`injection_limits`. Значение постоянно на всём горизонте: суточная ставка, а не
годовой объём и не разовая квота.

Проверяемое неравенство одно и то же на каждом шаге управления `k`:

```
Σ закачка(k) ≤ Σ добытая вода(k − лаг) · доля + n · длительность шага(k)
```

Оно живёт в валидаторе расписания
(`backend/domain/schedule/validate_dynamic.py`) и в потолке закачки поисковика
(`backend/application/optimization/schedule_search.py`), поэтому `n` не просто
попадает в отчёт, а расширяет пространство допустимых расписаний.

**Доля не обязательна.** Кейс, где задан только `n`, — допустимый кейс:

```json
{ "infrastructure": { "external_water_m3_per_day": 5000.0 } }
```

В этом случае `water_reinjection_fraction` подставляется равной `1.0`: вся
добытая вода считается вернувшейся в пласт, а `n` добавляется сверху. Это
самое мягкое из физически осмысленных допущений — оно не выдумывает воду,
которой нет, но и не отнимает у оптимизатора воду, про которую организаторы
ничего не сказали.

Подстановка не бесшумна. Политика воды
(`backend/core/contracts/constraints.py`) возвращает флаг `fraction_defaulted`:
`true` — долю выбрали мы, `false` — доля пришла из файла кейса. Отчёт по кейсу
обязан показать этот флаг: число, выбранное нами за организаторов, должно быть
видно как наше решение, а не выдаваться за исходные данные.

**«Ограничения нет» — это отдельное утверждение.** Молчание о доле больше не
означает «баланс воды не проверяется»: раз задан `n`, источник воды ограничен, и
неравенство выше проверяется. Чтобы отключить проверку целиком, ограничение
снимают явно:

```json
{ "infrastructure": { "water_supply_unlimited": true } }
```

При `water_supply_unlimited: true` объём закачки ограничен только физикой дека,
`injection_limits` и коридором компенсации.

Флаг несовместим с самими водяными параметрами: `water_supply_unlimited: true`
вместе с `external_water_m3_per_day`, `water_reinjection_fraction` или
`water_reinjection_lag_steps` — **ошибка**. Это противоречие («источник не
ограничен» и тут же «вот его объём»), и разрешать его догадкой нельзя: кейс
отклоняется с указанием обоих ключей.

Сводка:

| Что записано в `infrastructure` | Доля | Баланс воды |
| --- | --- | --- |
| ни одного водяного ключа | — | не проверяется |
| `water_supply_unlimited: true` | — | не проверяется, ограничение снято явно |
| только `external_water_m3_per_day` | `1.0`, `fraction_defaulted = true` | проверяется |
| `water_reinjection_fraction` задан | из файла, `fraction_defaulted = false` | проверяется |
| `water_supply_unlimited: true` + любой водяной ключ | — | ошибка |

`water_safety_factor` к этой таблице не относится: он не включает и не выключает
проверку баланса воды, а лишь умножает уже посчитанный потолок.

## Пример: кейс с возмущениями

```json
{
  "injection_limits": { "2010": 42000.0 },
  "liquid_limits": { "2010": 38000.0, "2011": 36000.0 },
  "production_floors": { "2010": 1500.0 },
  "oil_limits": { "2010": 2600.0 },
  "watercut_limits": { "2012": 0.95 },
  "well_outages": [
    { "well": "P12", "control_step_from": 48, "control_step_to": 51 }
  ],
  "infrastructure": {
    "external_water_m3_per_day": 5000.0,
    "external_water_m3_per_day_source": "organizer",
    "bhp_producer_min_bar": 90.0,
    "bhp_producer_min_bar_source": "organizer",
    "compensation_min": 0.9,
    "compensation_min_source": "diagnostic",
    "compensation_max": 1.1,
    "compensation_max_source": "diagnostic",
    "compensation_enforcement": "hard",
    "compensation_scope": "field_and_groups"
  }
}
```

Здесь `water_reinjection_fraction` не задан, поэтому доля подставляется равной
`1.0` и в отчёте помечается как выбранная нами: закачка ограничена суммой
«вся добытая вода + 5000 м³/сут», коридором компенсации и `injection_limits`.
`bhp_injector_max_bar` тоже не задан и берётся из умолчания дека — `300.0` бар
с источником `organizer`. Нижний предел добывающих поднят до `90.0` бар: если
организаторы объявят такое требование, расписание, ранее принятое при `50.0`,
будет отклонено.
