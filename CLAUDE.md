Если её нет — сказать пользователю и остановиться, работать без нее нельзя: карточки заданий и `docs/context/08_contracts.md` живут только там.

Дальше: **спросить пользователя, если не сказано явно, чья это сессия** — Савелий, Андрей, Иван или Михаил. Открыть `../docs/v2/assignments/<имя>.md` и прочитать целиком. **Первая версия закрыта и лежит в архиве.** `../docs/v1/` — 65 задач, персональные пакеты и каталог отвергнутых вариантов. Открывать только за историей решения; планом работ архив не является, и реализовывать что-либо по нему нельзя.

## Порядок чтения, обязательный

1. `../docs/v2/assignments/<имя>.md` — что делать и в каком порядке.
2. `backend/core/contracts/README.md` — точная форма всех общих типов: имена полей, единицы, оси, инварианты.
3. `backend/core/contracts/*.py` — те же типы, но исполняемые. **Импортировать их, не переизобретать.** `from backend.core.contracts import Schedule, StateAtDate, IntervalResponse, ...`.
4. Разделы `../docs/context/08_contracts.md`, на которые ссылается карточка (§N) — там объяснено, почему контракт именно такой, а не просто какой он.

Если контракт неясен из `backend/core/contracts/*.py` и `backend/core/contracts/README.md` — смотреть `docs/context/08_contracts.md`, не гадать и не придумывать своё поле.

## У ЧДД есть эталонная реализация — сверяться с ней, а не с интуицией

`../docs/models/CHDD_PYTHON/` — расчётчик организаторов, считающий «по той же методике, что применяется при оценке». Проверяющая сторона считает **этим кодом**, поэтому расхождение с ним — наш дефект по определению, спорить не о чем. Формат его входа (`REQUIRED_COLUMNS` в `chdd_model.py`) задаёт состав нашей выгрузки из симулятора, а `input/Нормативы_ЧДД.xlsx` — источник значений нормативов.

Контракты синхронизированы с ним 15.08. Четыре вещи до этой даты были в них неверны, и если увидишь их в чужом коде или в старой ветке — это ошибка:

| Неверно | Верно |
|---|---|
| `FCF = EBITDA − CAPEX` | `FCF = EBITDA − налог_на_прибыль − CAPEX`, налог 25% на **годовой** базе |
| Перевод под закачку `5.0 млн + ЭЦН` | Ровно `5.0 млн`, целиком в OPEX, ЭЦН не добавляется |
| Первый ЭЦН вводимой скважины в CAPEX | Первичное оснащение не начисляется вовсе |
| Нормативы годовым рядом (`by_year`) | Один скалярный набор на весь горизонт |

Плюс два правила, которых раньше не было нигде: потолок `SET_LRAT` в 500 м³/сут (`MAX_LRAT_M3_PER_DAY`, проверяется конструктором `ControlEvent`) и исключение строк с отрицательным месячным приростом (`is_excluded_by_negative_rule`). Второе применять обязательно, даже когда собственные приросты заведомо неотрицательны — почему, написано в докстринге функции.

## Установка

```bash
cd aios
python3 -m venv .venv && .venv/bin/pip install -e ".[dev]"
.venv/bin/pytest backend/core/contracts/tests   # контракты уже проверены, все зелёные — стартовая точка
```

Новый модуль класть в свой слой `backend/` (`ARCHITECTURE.md`: `core` → `domain` → `ml`/`infrastructure` → `application` → `presentation`). Отдельной строки в `pyproject.toml` больше не нужно: пакеты собираются `[tool.setuptools.packages.find]` по маске `backend*`. Направление зависимостей стережёт `tests/architecture/test_layers.py` — импорт вверх по слоям роняет тест.

## Жёсткие правила репозитория

1. **`backend/core/contracts/` правит только интегратор — Савелий.** Всем остальным: нужна правка типа — заводится issue, самовольно не редактировать. Если контракта не хватает для задачи — не подгонять под себя, остановиться и сообщить, что нужна правка контракта.
2. **Каждый пишет только в своих каталогах**, даже ради однострочной правки в чужом. Кто чем владеет — в персональных карточках `../docs/v2/assignments/<имя>.md`; `README.md` §2 даёт разбиение по пакетам, но имён владельцев не перечисляет.
3. **Моков нет.** Компонент, который не может посчитать, бросает исключение (`NotImplementedError` — законно). `return 0.0`, `return None`, случайный тензор нужной формы — запрещены. Единственное исключение из правила — `RunResult`: падение симулятора это статус, не exception.
4. **Синтетические данные** — только для проверки формы и сериализации, никогда в метриках качества, и помечаются в метаданных.
5. **Производное не хранится.** Типоразмер ЭЦН, стоимости событий, ЧДД — вычисляются, не лежат полем рядом с исходными данными.
6. **Ветки `feat/<имя>/<номер-задачи>`**, PR в `main`. Не ребейзить чужие ветки.
7. **Приёмка задачи — тест в своём каталоге.** Что именно проверяется, написано в карточке задачи (`docs/v2/tasks/`) в разделе «Приёмка» — это и есть содержание теста, а не вольная трактовка.
8. **Закрыл задачу — отметь её.** Последним действием сессии: `../docs/v2/STATUS.md`, строка своей задачи, колонка «Статус» → `готово ДД.ММ · <хеш коммита>`. Отдельным коммитом в `docs` с сообщением «<номер> закрыта». **`готово` ставится только при зелёном приёмочном тесте** — не «я закончил» и не «осталось причесать»; иначе `в работе` и словами, что осталось. Это единственное место, где живёт прогресс: ни в карточках задач, ни в персональных файлах его нет.

## Две шкалы времени — самая частая ошибка проекта

Дек живёт на 371 дате (`deck_date_index` 0…370), управление — на 225 датах (`control_step` 0…224), но **подтверждённых интервалов только 224** (`control_step` 0…223) — у шага 224 нет наблюдаемого месяца и он не несёт решений. Оба типа отклика (`StateAtDate` — по дате дека, `IntervalResponse` — по интервалу управления) уже разведены в `backend/core/contracts/response.py` ровно для того, чтобы эту ошибку нельзя было сделать на уровне типов. Не сворачивать их обратно в один тензор.

Полная форма — `backend/core/contracts/README.md` §1.2.

Не выбирать самому, какая версия правильная. `docs/context/08_contracts.md` содержит журнал решений (`context/07_concept.md` §9) — искать там дату последнего изменения этого куска и опираться на неё. Если после этого всё ещё неоднозначно — сообщить пользователю, не гадать.
