# aios — трек 2

Мультиагентная система управления фондом скважин с нейросетевым суррогатом. Model_Z: 103 скважины, управление с 01.01.2007, 225 управляющих дат при 224 наблюдаемых интервалах, целевая функция — максимизация ЧДД.

Постановка задачи, роли, концепция и разбор материалов организаторов — в репозитории документации `aios-hack/docs`. Здесь код.

---

## 1. Что это за система

Система принимает состояние месторождения и набор ограничений кейса, формирует режимы работы каждой скважины на горизонте управления и отдаёт два результата: файл расписания `wells_schedule.inc`, пригодный к расчёту гидродинамической моделью без ручного редактирования, и заявленное значение ЧДД, посчитанное по Методике организаторов.

Управляющие воздействия ограничены режимами фонда: открыть или закрыть скважину, изменить отбор жидкости, изменить объём закачки, перевести добывающую скважину под закачку. Геолого-технические мероприятия в задачу не входят.

Ключевое требование к результату — совпадение заявленного ЧДД с расчётом проверяющей стороны. Организаторы выложили эталонный расчётчик (`docs/models/CHDD_PYTHON/`), считающий по той же методике, что применяется при оценке. Поэтому расхождение с ним считается нашим дефектом по определению, а схождение — главный аргумент качества (§7).

## 2. Архитектура и границы пакетов

Каталоги соответствуют пакетам работ, у каждого один владелец. Пересечений по файлам нет: ветки, трогающие непересекающиеся деревья, вливаются без конфликтов.

```
contracts/                            общие типы, единственная общая поверхность
schedule/   economics/                расписание и ЧДД
bridge/     surrogate/   optimizer/   мост к симулятору, суррогат, оптимизатор
connectivity/  policy/  robustness/   связность, политики, устойчивость
config/                               конфигурация и seed
ui/         llm/                      интерфейс и слой интерпретируемости
aios_cli/                             командные точки входа образа
data/                                 вне git, адресуется хешами
```

Поток данных между пакетами идёт только через типы из `contracts/`:

```
дек организаторов ──parse──> Schedule ──emit──> wells_schedule.inc
                                │
                                ├──> OpmDeckEmitter ──> OPM ──> StateAtDate[371]
                                │                              IntervalResponse[224]
                                │                                      │
                                └──────────────────────────────────────┴──> NpvTable
```

`Schedule` и `NpvTable` — самые потребляемые контракты: их читают все остальные пакеты. Точная форма всех общих типов — `contracts/README.md`: имена полей, единицы, порядок осей, инварианты. Типы там исполняемые (`contracts/*.py`), их следует импортировать, а не переизобретать по markdown.

**Корневые файлы** (`Dockerfile`, `docker-compose.yml`, CI, этот `README.md`) принадлежат интегратору: они пересекают все пакеты и потому не могут принадлежать ни одному из них.

## 3. Установка и запуск

### Нативно

```bash
python3 -m venv .venv
.venv/bin/pip install -e ".[dev]"
.venv/bin/pytest
```

Требуется Python 3.11 или новее. Единственная внешняя зависимость расчётной части — `openpyxl` (чтение нормативов из xlsx); при её отсутствии загрузчик разбирает xlsx силами стандартной библиотеки, значения те же.

**Данные организаторов в репозиторий не входят** и не могут в него входить: подменять их запрещено, а вес дека — десятки мегабайт. Репозиторий документации `aios-hack/docs` с каталогом `models/` должен лежать рядом (сиблингом) либо указываться переменной окружения:

```bash
AIOS_DOCS_ROOT=/путь/к/aios/docs .venv/bin/pytest
```

Без данных тесты не падают, а пропускаются: `119 passed, 122 skipped`. С данными — `241 passed`.

### В Docker

Образ собирается для полного репозитория. Данные организаторов монтируются снаружи и в образ не копируются.

```bash
docker build -t aios:latest .

# что попало в образ и какие данные видны
docker run --rm -v /путь/к/aios/docs:/data/docs:ro aios:latest selfcheck

# тесты
docker run --rm -v /путь/к/aios/docs:/data/docs:ro aios:latest tests -q

# расчёт ЧДД со сверкой с эталонным расчётчиком
docker run --rm -v /путь/к/aios/docs:/data/docs:ro -v "$PWD/out:/out" aios:latest npv

# эмит wells_schedule.inc
docker run --rm -v /путь/к/aios/docs:/data/docs:ro -v "$PWD/out:/out" aios:latest emit

# веб-интерфейс
docker run --rm -p 8000:8000 -v /путь/к/aios/docs:/data/docs:ro aios:latest web
```

То же через compose (тонкие именованные обёртки над тем же входом, не второй механизм):

```bash
AIOS_DOCS=/путь/к/aios/docs docker compose run --rm tests
AIOS_DOCS=/путь/к/aios/docs docker compose run --rm npv
```

**Устройство образа.** Две стадии: `node:22.11.0-bookworm-slim` собирает фронт `ui/web` (`npm ci && npm run build`), `python:3.12.7-slim-bookworm` обслуживает расчёт и отдаёт собранную статику. Точка входа — `docker/entrypoint.sh` со свободным `CMD`, выбирающим команду; варианты перечислены выше, плюс `shell` и произвольная команда.

Если каталога нет в срезе репозитория, из которого идёт сборка, стадия пропускается корректно, а состав образа печатается на сборке (`RUN python -m aios_cli.selfcheck`) — видно, что найдено, а что отсутствует. Команда, которой не хватает пакета или данных, отказывается работать явным кодом возврата (`2` — нет данных организаторов, `3` — нет собранного фронта), а не считает молча.

## 4. Воспроизводимость

Требование организаторов: повторный запуск в идентичной среде с теми же данными даёт сопоставимый результат, скрытых зависимостей от внешних ресурсов нет, неконтролируемых случайных параметров нет, seed зафиксирован.

Что сделано:

- базовые образы запинены по тегу (`node:22.11.0-bookworm-slim`, `python:3.12.7-slim-bookworm`), а не по `latest`;
- `pip`, `setuptools`, `wheel`, `openpyxl`, `pytest` ставятся точными версиями;
- `PYTHONHASHSEED=0` и `AIOS_SEED=20260816` заданы в образе; seed печатается в выводе расчёта и попадает в `npv.json`;
- данные организаторов не копируются в образ и не подменяются — только монтируются только на чтение;
- расчётный тракт детерминирован: два прогона `npv` на одном образе и одних данных дают побайтно идентичный `npv.json` (проверено);
- каноническая сериализация расписания — JSON по RFC 8785, поэтому одинаковое расписание даёт одинаковые байты и одинаковый хеш независимо от порядка построения.

Собственного источника случайности в `schedule/` и `economics/` нет вообще: обе библиотеки детерминированы по входу.

## 5. Контракты и две шкалы времени

Это самая частая ошибка проекта, и она не даёт ни исключения, ни абсурдного числа — она даёт правдоподобный ЧДД, посчитанный не по тем месяцам.

| Шкала | Диапазон | Начало | Кто на ней живёт |
|---|---|---|---|
| Дек | 371 дата, индексы 0…370 | 01.11.1994 | `StateAtDate`, автомат ЭЦН |
| Управление | 225 дат 0…224, **224 замкнутых интервала** 0…223 | 01.01.2007 | `Schedule`, `IntervalResponse`, `NpvTable` |

Дата управляющего шага: `deck_date_index = 146 + control_step`. Интервал — не то же самое, что дата:

```
interval[k] = [DATES[146 + k], DATES[147 + k])
volume[k]   = cumulative[147 + k] − cumulative[146 + k]     для k = 0…223
```

Управляющих дат 225, замкнутых интервалов 224: у последней даты (01.09.2025) следующей нет, поэтому шаг 224 — терминальное состояние без наблюдаемого месяца и без денег. Он не несёт управляющих решений и отсутствует в разложении ЧДД по месяцам.

Отклик симулятора разведён на два типа именно ради этой границы: `StateAtDate[371]` (мгновенные величины по датам дека) и `IntervalResponse[224]` (помесячные объёмы по интервалам управления). Свернуть их обратно в один тензор — воспроизвести ошибку выравнивания на уровне типов.

**Расписание — два слоя.** Внутри управляющего горизонта лежат не только режимы фонда: 25 блоков заканчивания `COMPDAT` (из 60 в деке целиком), один `WPIMULT` и ввод 22 скважин, ранее не появлявшихся в `WCONPROD`/`WCONINJE`. Это данные месторождения, а не решения агента: они переносятся в выходной файл без изменений и не являются рычагом. Парсер, считающий управляемым весь текст после t0, выдаёт файл, который прогонится и даст неверный результат без единой ошибки.

Полная спецификация — `contracts/README.md`.

## 6. Вход, выход, параметры

**Вход:**

| Что | Откуда | Формат |
|---|---|---|
| Дек Model_Z | `docs/models/Model_Z/` | Eclipse-совместимый текст, `Model_Z_sch.inc` — секция SCHEDULE |
| Нормативы Методики | `docs/models/CHDD_PYTHON/input/Нормативы_ЧДД.xlsx` | xlsx, источник истины по числам |
| Отклик симулятора | прогон OPM либо суррогат | `StateAtDate[371]`, `IntervalResponse[224]` |
| Ограничения кейса | интерфейс | `Constraints`, сериализуемый документ |

**Выход:**

| Что | Куда | Формат |
|---|---|---|
| `wells_schedule.inc` | `/out` | текст, совместимый с ГГДМ |
| Заявленный ЧДД | `/out/npv.json` | JSON, поле `npv_methodology`, рубли |
| Разложения ЧДД | `NpvTable` | по годам, по интервалам, по скважинам |

**Параметры экономики** — один скалярный набор на весь горизонт, годовой оси нет. Цена нефти 28000 руб/т, отчисления 19600 руб/т, OPEX по нефти 40 руб/т, по жидкости 100 руб/т, по закачке 30 руб/м³, содержание фонда 1 млн руб/скв·год, замена ЭЦН 1.8 млн руб/операцию, событие остановки или запуска 1.0 млн руб, перевод под закачку ровно 5.0 млн руб, ставка дисконтирования 0.10, налог на имущество 0.022, налог на прибыль 0.25.

Три места, где легко ошибиться и где ошибка стоит денег: налог на имущество — статья OPEX, а не вычитание после EBITDA; налог на прибыль считается на **годовой** базе и разносится по месяцам пропорционально положительной месячной прибыли; первичное оснащение ЭЦН не оплачивается вовсе, а перевод под закачку стоит ровно 5.0 млн без стоимости насоса.

Ограничения, проверяемые до эмита: уставка отбора жидкости не выше 500 м³/сут (эталонный расчётчик на превышении падает с ошибкой), управляющих событий на терминальном шаге 224 нет, `CONVERT_INJ` по скважине не повторяется, событий по невведённой скважине нет.

## 7. Схождение с эталонным расчётчиком — главный аргумент качества

Организаторы ранжируют по ЧДД и выполняют **один** расчёт: одна попытка, повторных прогонов нет. Поэтому схождение с их расчётчиком сделано не разовой сверкой, а постоянной приёмкой в тестах.

Как устроено (`economics/tests/test_reference_parity.py`, 14 тестов):

- **11 сценариев** прогоняются через нашу реализацию и через эталонный расчётчик организаторов одновременно, результаты сравниваются постатейно, а не только по итоговому числу. Сценарии закрывают разобранные ловушки: базовая добыча, год с убыточным месяцем и годовая база налога, правило исключения строк с отрицательным приростом, перевод под закачку, остановка и повторный запуск, ввод скважины внутри горизонта, ввод ровно на первом управляющем шаге, разгон ЭЦН с историей до t0, понижение типоразмера ниже порога, ненулевая остаточная стоимость с амортизацией, опция начисления первичного ЭЦН;
- **внешняя сверка на данных организаторов** — `Пример_исходных_данных.xlsx` из поставки расчётчика загружается их же кодом (`excel_io.load_source_records`), считается обеими реализациями и сравнивается. Это проверка на их данных их загрузчиком, а не на наших синтетических рядах;
- **машинный ноль.** На примере организаторов расхождение составляет `1.49e-08` руб при ЧДД `5.41e7` руб — это предел точности double, а не близость с допуском. Сверка постатейная: выручка, отчисления, OPEX по статьям, налоги, EBITDA, FCF, дисконт;
- **негативный контроль** — отдельный тест внедряет искусственное расхождение и проверяет, что сравнение его ловит. Без него зелёный отчёт о схождении ничего не доказывает.

Тот же расчёт выполняется в контейнере командой `npv` и печатает расхождение с эталоном явным числом.

Косвенные оракулы дополняют сверку и работают без данных: два сценария храповика ЭЦН (`80 → 100 → 125` = 8.65 млн против `80 → 125` = 4.55 млн), тесты автомата состояний фонда, налоговые тесты (убыточный год даёт нулевой налог, год с убыточным месяцем считается по годовой базе), тест размерности при начислении OPEX по жидкости, тест правила отрицательных строк, тест потолка `LRAT = 501`.

Таблица порогов рентабельности из карточки задачи 11 отдельным тестом **не покрыта** — оракулом схождения служат эталонный расчётчик и перечисленные выше проверки.

Расписание проверяется собственным жёстким оракулом: `parse → emit` восстанавливает исходный файл **байт в байт** (1553298 байт, 371 дата, 370 блоков `WCONPROD`).

**Заблокировано, и это надо читать как состояние, а не как недоделку:**

- **`SubmissionEmitter` (задача 62B) не реализован.** Формат `wells_schedule.inc`, который принимают организаторы, не подтверждён. Форма артефакта зафиксирована в `contracts/simulation.py` на будущее, но эмиттера нет: правильный хеш рядом с неверно эмитированным файлом проверку не проходит, а угадывать формат при единственной попытке расчёта нельзя. Разблокируется ответом организаторов.
- **Цепочка OPM: прогонов нет.** Ни одного отклика симулятора на нашем расписании не получено. Следствия: `validate_dynamic` (задача 17) не реализован — он принимает на вход `StateAtDate`/`IntervalResponse`, которых нет; экономический разбор базового сценария (задача 13) не сделан по той же причине. Схождение с эталоном (§7) проверено на данных организаторов и на 11 сценариях, но не на отклике полной гидродинамической модели — этого отклика пока не существует.
- **Веб-интерфейс в образе не собран в текущем срезе.** Каталог `ui/web` принадлежит другому пакету работ и в эту ветку не влит. Стадия сборки фронта написана и пропускается корректно; проверить её на реальном `ui/web` в этой ветке было невозможно.
- **Суррогат, оптимизатор, связность, политики, конфигурация** — другие пакеты работ, в этой ветке отсутствуют. Строки о них в §2 описывают целевую структуру полного репозитория.

## 10. Правила репозитория

1. **`contracts/` правит только интегратор.** Нужна правка типа — issue, не коммит.
2. **Каждый пишет только в своих каталогах**, даже ради однострочной правки.
3. **Зависимости по пакетам, не общим лок-файлом.**
4. **Ветки `feat/<имя>/<номер-задачи>`**, вливание через PR в защищённый `main`.
5. **Приёмка задачи — тест в своём каталоге.**
6. **Моков нет.** Компонент, который не может посчитать, бросает исключение. Возврат нуля, `None` или случайного массива нужной формы запрещён. Единственное исключение — падение симулятора, оно передаётся статусом в `RunResult`.
7. **Неотвеченный вопрос организаторам — политика с реальными реализациями по каждой ветке,** а не заглушка.
8. **Производное не хранится.** Типоразмер ЭЦН, стоимости и ЧДД внутри расписания отсутствуют.
9. **`data/` в git не кладётся.** Артефакты прогонов и датасеты живут снаружи и адресуются хешами.

## 11. С чего начать

**Если запускаешь агента (Claude Code) — он сам прочитает `CLAUDE.md` в этом каталоге.** Ниже — то же самое для человека.

Прочитать `contracts/README.md` целиком: там точная форма всего, что пересекает границы пакетов. Затем свою карточку в `docs/assignments/`.

Импортировать `from contracts import ...`, не переизобретать типы по markdown заново — расхождения в названии поля между независимо написанными реализациями уже находили и правили руками несколько раз, отсюда и пакет.

Отдельно обратить внимание на две шкалы времени (§5) и на два слоя расписания: ошибка в первом даёт правдоподобный неверный ЧДД, ошибка во втором — файл, который прогонится и посчитает не то месторождение.
